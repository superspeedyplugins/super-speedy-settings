# SSP (super-speedy-settings) MCP plan — the `ssp` ability surface

**Date:** 2026-07-21 · **Status:** 🟡 approved direction, not started · **Size:** M
(the security design is the work, not the code)
**Pattern:** `plugin-mcp` + `wp-abilities-api` skills; SSE is the production reference. Role
numbers refer to the demo repo's `.docs/2026-07-21-mcp-rollout-plan.md` §8 template.
**Prior analysis:** `.docs/2026-07-20-mcp-gap-plugin-provisioning.md` (this doc supersedes
its "options" section — the ability path is chosen).
**This is the bootstrap:** Dave installs ONE Super Speedy plugin by hand and enters the
licence; every other plugin then installs over MCP. It ships in this shared submodule, so
one implementation reaches all nine plugins via the normal settings-sync flow.

## Namespace, category, caps, dedupe

- Namespace `ssp`, category `super-speedy-settings`.
- Caps: `ssp_manage` (reads), `ssp_install` (Tier 3). `user_has_cap` grant to
  `manage_options`.
- **Dedupe guard:** every plugin carries this submodule, so registration MUST be
  once-per-site: guard on a shared constant/static (same pattern as
  `SuperSpeedySettings_1_0` itself — first loader wins), or nine copies of each ability
  fight. This is the one registration gotcha unique to the submodule.
- Version-gate on `function_exists('wp_register_ability')`.

## Abilities

| Ability | Tier/Role | Notes |
|---|---|---|
| `licence-status` | 1 / 3 | current licence, what it covers, expiry/renewal state |
| `list-installable` | 1 / 1 | slug, name, installed?, active?, installed version vs latest on the update server. The agent's shopping list |
| `install-plugin {slug, confirm}` | 3 / 11 | resolve the zip from the UPDATE SERVER using the site's own licence; `Plugin_Upgrader`; activate; return installed version + activation errors. Also serves as update-plugin when already installed |
| `activate-plugin` / `deactivate-plugin {slug, confirm}` | 3 / 11 | deactivate needs confirm; activate of an installed SSP plugin is low-risk but keep the confirm for symmetry |

## Security (this section is the feature)

An "install code" endpoint is remote code execution unless constrained. Hard rules:

1. **The caller NEVER supplies a URL.** Input is a slug from `list-installable`; the zip
   URL is resolved server-side from the licensed update server. No override, no filter
   that widens it.
2. **Host allowlist enforced at download time** (superspeedyplugins.com / the update
   endpoint), belt-and-braces behind rule 1 — a redirect off-host aborts.
3. Slug allowlist = the licence's product list. Unknown slug → `ssp_not_licensed`.
4. `ssp_install` cap + `confirm:true` + an audit log row per install (who, slug, version,
   result) readable via a Tier-1 `list-install-log` if wanted later.
5. Signature/checksum of the zip if the update server can serve one (it should — note for
   the auth-server side); otherwise TLS + host pinning is the floor.
6. Failure surfaces the real upgrader error message — silent half-installs are the worst
   outcome on a remote box nobody can shell into.

## Rollout

Ships in the submodule → propagates via the settings-sync skill flow (Dave pushes the
submodule; each plugin bumps). The auth/update server may need a "resolve zip for licence"
endpoint if the existing update path can't be reused — flag for Dave, auth-server is his.

## Tests

SSE-style numbered harness inside ONE carrier plugin's test suite (imports is the natural
host): licence-status/list-installable against a licensed test site; install-plugin gates
(no confirm, unlicensed slug, off-host redirect aborts); dedupe guard (two plugins loading
the submodule register ONE set); permission denial. Bridge E2E: fresh box + one plugin →
install the rest.
